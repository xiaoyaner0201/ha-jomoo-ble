# ha-jomoo-ble

[English](README.md) · Apache-2.0 · 非官方 Home Assistant 自定义集成

在 Home Assistant 里通过本地蓝牙控制 **九牧 ZS800J** 智能马桶。蓝牙可以走 HA 本机任意可连接的蓝牙适配器，也可以走放在马桶旁边的 ESPHome 蓝牙代理。不连云端，不用账号，不含任何厂商代码。

## ⚠️ 0.4.0 不兼容变更

**使用过淋浴守护的用户必须迁移。** 本版移除
`jomoo_ble.suspend_auto_cover` / `jomoo_ble.resume_auto_cover`，自动翻盖开关的
`guard_active`、`guard_pending`、`guard_previous` 属性，以及「淋浴守护生效中」二元传感器。
旧蓝图、调用这两个服务或引用这些传感器/属性的自动化都会受影响。

设备集成只暴露设备能力：实体、设备动作和设备页面。「出热水时暂停设置，停水后恢复」
属于跨设备策略，应由用户在 Home Assistant 自动化、脚本或蓝图中配置，不应放在设备集成内。
新版蓝图使用 HA 原生场景快照与恢复，不再调用集成专用的守护服务。

### 从 0.3.x 或更早版本迁移

1. 升级前停用旧自动化；若正在暂停，先检查并按需恢复自动翻盖。升级本身绝不恢复或写入设备设置。
2. 更新集成并重启 HA。启动时尽力清理旧策略存储和旧传感器注册记录；若旧暂停处于生效/待确认状态，
   只记一条提醒检查自动翻盖的警告，不会把旧记录转换成场景，也不会连接设备执行恢复。
3. 从原路径重新导入/更新蓝图，编辑或重建自动化：将旧 `toilet` 输入改为 `switches`，
   选择**自动翻盖**和**脚感**。只需启用已验证的控制，无需实验开关。
   默认恢复延迟为 **10 分钟**；每份自动化使用独立、专用的 `scene_id`。
4. 删除或替换调用已移除服务的自动化；移除引用 `guard_active` / `guard_pending`
   或旧传感器的兜底自动化。快照仍存在时的恢复检查已包含在新版蓝图内。
5. 验证一次完整的出热水 → 停水 → 恢复，包括原本关闭的开关仍保持关闭。
   已有脚感实体的 entity_id 不变（即使名字含 experimental），只更新显示名；
   仅解除旧版本由集成默认设置的禁用，用户自己禁用的实体保持禁用。

最小 HA 原生模式如下，实体名请替换为实际值。出热水时执行暂停脚本，停水满设定时长后执行恢复脚本；
蓝图在此基础上增加逐开关容错和有界暂停尝试。

```yaml
script:
  toilet_pause:
    sequence:
      - condition: template
        value_template: "{{ states.scene.jomoo_shower_guard_before is none }}"
      - action: scene.create
        data:
          scene_id: jomoo_shower_guard_before
          snapshot_entities:
            - switch.toilet_auto_cover
            - switch.toilet_foot_sensor
      - action: switch.turn_off
        target:
          entity_id:
            - switch.toilet_auto_cover
            - switch.toilet_foot_sensor
  toilet_restore:
    sequence:
      - condition: template
        value_template: "{{ states.scene.jomoo_shower_guard_before is not none }}"
      - action: scene.turn_on
        target:
          entity_id: scene.jomoo_shower_guard_before
      - action: scene.delete
        target:
          entity_id: scene.jomoo_shower_guard_before
```

**`scene.create` 创建的场景无法跨 HA 重启或场景重载保留。** 暂停期间重启后，不能自动恢复原值。
需要跨重启记忆时，请在自己的自动化中为每个开关配置一个持久 `input_boolean`，或者重启后人工检查。
暂停期间手动改开关不再取消快照，恢复时仍会应用保存的状态。恢复是尽力而为，出现错误后要检查追踪和开关。
详情见下文「淋浴守护（HA 原生）」。

## 为什么做这个

淋浴区附近的自动翻盖可能受动作或水汽影响，在出热水时反复打开。Home Assistant 可以暂停自动翻盖和脚感，
停水后恢复成原来的状态——本来关闭的设置仍然关闭。集成只提供设备能力，
[HA 原生蓝图](blueprints/automation/jomoo_ble/shower_guard.yaml) 提供可选、由用户配置的联动策略。

协议实现根据通信帧观察、只读查询和读回结果独立编写，并与官方控制器的行为核对，
不包含、也不需要厂商源码或小程序文件。开关盖、翻圈、小冲、自动翻盖和脚感关/开均有实机读回验证，其他设置保持不变。

## 能做什么

- **按需读取状态**：
  - 上盖和座圈的位置，是否在运动；
  - 是否有人就座、是否在冲水、当前工作状态；
  - 缺水、水流异常、传感器或过温故障；
  - 滤芯剩余百分比和已用小时、泡沫液不足；
  - 各项设置档位，以及上次刷新时间。
- **已验证的控制**：开盖、关盖、开座圈、关座圈、小冲，以及「自动翻盖」「脚感」开关。
- **HA 原生淋浴守护蓝图**：快照一个或多个开关，出热水时暂停，停水后恢复原值；策略由 HA 自动化配置，不在集成内。
- **实验性控制**（默认关闭）：
  - 档位类：水温、座温、暖风温度、臀洗水压、臀洗喷嘴位置、暖风风速、宽幅洗；
  - 开关类：自动冲水、自动夜灯、UV 水路杀菌、关盖冲水、自动小冲、氛围灯；
  - 动作类：大冲。

## 硬件

- **马桶**：九牧 ZS800J，蓝牙广播名是 `JOMOO_SMART_237369`。其他型号会被拒绝。
- **蓝牙连接**：HA 到马桶之间要有一条能主动连接的蓝牙链路，可以是本机蓝牙适配器，也可以是开了 `active: true` 的 [ESPHome 蓝牙代理](https://esphome.io/components/bluetooth_proxy/)。
  - 卫生间对蓝牙信号衰减很大，代理要放在马桶附近。实测隔墙约 -90 dBm 时基本连不上，放到旁边约 -68 dBm，不到 1 秒就能连上。
  - 注意防水和用电安全。
  - 用 ESPHome 代理时，还要在 HA 里打开这台 ESPHome 设备的集成选项，把「蓝牙扫描模式」设为「主动」。新版 HA 默认是「自动」，大部分时间只被动扫描，马桶的名字（只放在扫描响应里）到不了 HA。这时集成会把它当成不支持的型号拒绝连接，重载后所有实体都会变成不可用。ESPHome 配置里写 `active: true` 管不到 HA 这一侧的设置。

## 先知道两件事

1. **每次连接，马桶都会「嘀」一声。** 所以集成默认不轮询，默认只在下面三种情况下短暂连接，用完立刻断开：
   - 点「刷新状态」；
   - 调用 `jomoo_ble.refresh`；
   - 执行控制。
   如果需要，可以在选项里显式开启定时刷新（间隔 300 秒到 24 小时），或持续实时状态。
2. **同一时间只能有一个设备连马桶。** HA 连着时，官方小程序连不上，反过来也一样。启用持续实时状态后，HA 会持续持有这个连接。添加集成前请先关掉小程序。

## 安装

**通过 HACS 安装（自定义仓库）**：
1. 打开 HACS → 集成 → 右上角 ⋮ → 自定义存储库；
2. 填入 `https://github.com/xiaoyaner0201/ha-jomoo-ble`，类别选「集成」；
3. 安装后重启 HA。

**手动安装**：把 `custom_components/jomoo_ble` 整个目录（含 `lib/`）复制到 HA 的 `config/custom_components/` 下，然后重启 HA。

**添加设备**：
- 进入「设置 → 设备与服务」，马桶通常会被自动发现。
- 如果没有被发现，点「添加集成 → JOMOO BLE」，填入马桶的蓝牙 MAC 地址。只要附近能看到匹配的广播，这一栏会自动填好。文档里的 `02:00:00:00:00:01` 是虚构的示例地址。
- 添加时会做一次只读查询，马桶会嘀一声。

## 选项

| 选项 | 默认 | 含义 |
| --- | --- | --- |
| 启用已验证的控制 | 关 | 翻盖、翻圈、小冲、自动翻盖、脚感 |
| 启用实验性控制 | 关 | 下表中标为「实验」的全部功能 |
| 自动刷新间隔 | 0（关） | 填 0，或 300 到 86400 秒 |
| 持续实时状态 `enable_status_stream` | 关 | 持有一个共享 BLE 连接；启用时忽略轮询间隔 |

### 可选实时采集（已完成实机验收，默认关闭）

此功能仍默认关闭，需要在集成选项中明确开启「启用持续实时状态」。首次连接会响，且 HA 将持续占用唯一
central，官方小程序不能同时连接。关闭选项、卸载集成或停止 HA 才释放蓝牙；
若断开无法确认，阻断控制并显示诊断，不声称手机已经可以连接。

启动只尝试一次连接，初始查询完整且校验过的 E2/EA/E9/FA/E7 后，以被动通知
更新已有实体（含「冲水中」）。流、手动刷新、控制共享原 SessionManager
的同一物理连接和操作锁。控制仍每次全新查询，保留设置、只写一次并读回；
不拿流缓存拼控制帧。没有周期性查询/断开重连，也没有自动重连循环。
断线后相关状态 unavailable，点击已有「刷新状态」或明确调用 `jomoo_ble.refresh`
才允许一次合并恢复尝试；底层原有有界 establish 重试不叠加。

仅开启时新增「实时状态连接」「上次收到状态」两项诊断。接收时间只随合法包变化，
属性给出各帧时间；静默不冒充新状态，断线前缓存不继续当 live。
「上次刷新」仍表示主动完整查询完成时间。连接状态不是心跳，静默不能证明所有
字段仍然新鲜。FA payload[5] bit0 仍未知，没有命名为补水/水位/补满，没有新增
补水传感器，更没有泵策略或跨设备服务。联动由 HA 原生 automation 另行配置。

已在真实 HA 2026.9.1 中通过 ESPHome 蓝牙代理完成实机验收：冲水开始和结束
通过被动通知实时送达 HA，无需周期查询。5 个端到端实机场景全部通过，包括
自动化暂停期间 HA 重启后流重新建立。最终安装后，一个连接约 10.5 小时无掉线；
期间 9 次日常冲水全部送达 `flushing` on → off，冲水中、有人就座等实体无 unavailable。
单独维护的 HA 原生补水联动自动化（不在本仓库）据此在冲水结束后约 0.5 秒动作。
这不代表检测到了补水结束，也不构成长期稳定性保证；长期稳定性仍在观察。

若卸载失败，需人工检查蓝牙释放并重启 HA：HA 2026.9.1 会将 entry 标为
FAILED_UNLOAD，拒绝后续 reload。释放未确认前，不要假定手机已能连接。
完整语义与边界见[实时采集说明](docs/status-stream.md)。

| 实体 | 类型 | 状态 |
| --- | --- | --- |
| 刷新状态 | 按钮 | 已验证（只读） |
| 开盖 / 关盖 / 开座圈 / 关座圈 | 按钮 | 已验证 |
| 小冲 | 按钮 | 已验证 |
| 大冲 | 按钮 | 实验，默认禁用 |
| 自动翻盖、脚感 | 开关 | 已验证，注册表默认启用；配置开关，受已验证控制选项限制 |
| 自动冲水、自动夜灯 | 开关 | 实验，默认禁用 |
| UV 水路杀菌、关盖冲水、自动小冲、氛围灯 | 开关 | 实验，默认禁用 |
| 水温 / 座温 / 暖风温度档位、臀洗水压、臀洗喷嘴位置、暖风风速、宽幅洗 | 数值 | 实验，默认禁用（这些是设备档位，不是摄氏度） |
| 上盖、座圈、上盖运动中、座圈运动中、有人就座、冲水中 | 二元传感器 | 只读 |
| 缺水、水流异常、传感器或过温故障、滤芯需更换、泡沫液不足 | 二元传感器 | 只读 |
| 工作状态、滤芯剩余（%）、滤芯已用（h）、妇洗水压 / 喷嘴位置、上次刷新 | 传感器 | 只读 |
| 原始 E2 / FA / E9 / EA / E7 | 传感器 | 诊断用，默认禁用 |

**「已验证」和「实验」的区别**：
- 已验证：指令在真实的 ZS800J 上实际发过，读回设备状态确认生效，而且其他设置一个都没变。
- 实验：沿用同一套帧结构，但还没在真机上跑过。它同样会读回确认，设备没有确认就不会报成功。

**这台马桶的两个特性**：
- 盖子和座圈是联动的：开座圈会连带开盖，关座圈时盖子保持开着。
- 自动翻盖会感应站在马桶前的人，所以刚关好的盖子，如果有人站在前面，可能会自己再打开。

## 淋浴守护（HA 原生）

从原路径导入/更新 v0.4.0+ 蓝图：

[![在你的 Home Assistant 中打开蓝图导入对话框](https://my.home-assistant.io/badges/blueprint_import.svg)](https://my.home-assistant.io/redirect/blueprint_import/?blueprint_url=https%3A%2F%2Fgithub.com%2Fxiaoyaner0201%2Fha-jomoo-ble%2Fblob%2Fmain%2Fblueprints%2Fautomation%2Fjomoo_ble%2Fshower_guard.yaml)

输入：
- `hot_water`：正在出热水的二元传感器；
- `switches`：一个或多个开关，建议选「自动翻盖」和「脚感」，无需实验控制；
- `off_delay`：恢复延迟，默认 **10 分钟**；
- `scene_id`：每份自动化专用的场景对象名，默认 `jomoo_shower_guard_before`，不含 `scene.` 前缀。

启用已验证控制；首次快照前所有开关必须有明确的 on/off 状态。不要复用场景 ID，也不要在暂停中修改输入。
出热水 → 用 `scene.create` 的 `snapshot_entities` 保存原值一次 → 逐个关闭当前开着的开关。
重触发不会覆盖最初快照。每个开关独立容错，最多尝试 5 轮、间隔 30 秒；停水后提前结束等待。
这是 HA 自动化的状态协调尝试，不是集成内重发控制包。停水满延迟后执行 `scene.turn_on` 和 `scene.delete`
（已确认 HA 2026.9.1 提供该服务），同时恢复原来的开/关值。

**选信号要注意**：用来触发的必须是「正在用热水」，而不是「热水器通电」。接好以后先洗一次澡，看这个信号的历史记录确实变过、自动化的「上次触发」有时间，再放心用。

**实测搭配（已更正）**：验证搭配为国行史密斯燃气热水器，通过社区集成 [Ai-Link A.O. Smith](https://github.com/mopocv/Ai-Link_A.O.Smith) 接入 HA。要用 v1.4.0 及以上，它会自己续期 App 的短效令牌。

本文旧版推荐用它的「燃烧加热状态」，这是错的：这台机器上它连着好几天一直是「未加热」，真洗澡时风机约 3000 转、燃烧比例 44%，它也没变，守护一次都没触发。流量读数也不可靠，出现过没开水龙头、流量却不为零的情况。

已验证的信号是：**零冷水开着，或者风机转速大于 0**。零冷水循环和其他用热水的时候也会触发，只会让选中的开关暂停一会儿。实体名换成你自己的；两个来源都不可用时，模板保持原值，不会把「没数据」当成「停水」：

```yaml
template:
  - binary_sensor:
      - name: 正在用热水
        unique_id: hot_water_in_use
        state: >-
          {% set recirculation = states('switch.water_heater_recirculation') %}
          {% set fan = states('sensor.water_heater_fan_speed') %}
          {% if recirculation in ['unknown', 'unavailable'] and not is_number(fan) %}
            {{ this.state == 'on' }}
          {% else %}
            {{ recirculation == 'on' or (fan | float(0)) > 0 }}
          {% endif %}
```

蓝图默认恢复延迟已改为 **10 分钟**，避免热水使用刚结束就恢复感应。热水器云端数据也可能连续几分钟不更新。

### 恢复检查与重启限制

HA 重启或保存/重载自动化会丢弃正在运行的 `for:` 计时。蓝图在 HA 启动和每 5 分钟检查一次：
仅当停水满延迟、且原快照场景仍存在时，恢复并删除快照。因此只重载自动化、场景仍保留时可以补偿丢失的计时。
恢复分支不会重新快照，也不会猜测升级前或重启前的值。恢复还会等所有选中的开关可用（开/关）后才执行：
HA 会静默跳过不可用的实体，若在蓝牙掉线时恢复，快照会被删掉却什么都没恢复。因此快照会保留，
等马桶重新在线后，由下一次恢复检查完成恢复。

**动态场景无法跨 HA 重启或场景重载保留。** 启动触发器不能挽回丢失的快照。
暂停中重启后请检查自动翻盖和脚感；确需跨重启恢复，请在自己的自动化中为每个开关配置持久 `input_boolean`。
与已移除的集成内策略不同，手动改开关不再取消快照恢复。恢复是尽力而为，不是事务；
写入失败后请检查自动化追踪和实际设置。新版蓝图已在真实 HA 中用模拟马桶验证，不宣称新增完整实机淋浴验收。

## 安全设计

- **写之前先确认能写**：每次写入前，都会在同一次连接里读一遍 E2、FA、E9、EA 四组状态，马桶不在待机就拒绝。开关盖、翻圈、冲水这类动作，在有人就座、盖子或座圈正在动的时候也会拒绝。
- **只改要改的那一项**：功能帧携带完整设置，短选项帧只针对一项；两类控制均基于全新查询，并保留其他设置。
- **写完一定读回核对**：
  - 写完后会反复读，直到确认目标生效；
  - 然后逐项核对其他已知设置，只要有一项变了就报错，并给出前后差异。
- **冲水的确认方式**：冲水指令发出后，如果约 6 秒内没看到「冲水中」的标志，会记一条警告，结果标为「已发送、未确认」。
- **集成内绝不自动重试控制写入**：写入失败时指令也可能已经到了马桶，所以不会自动重发，也不会先把状态显示成「成功」。
- **断开状态不明就停用**：如果没法确认连接已经断开，集成会停止再发起连接。卸载失败时需人工检查蓝牙释放并重启 HA，不能保证重新加载即可恢复。
- **不做的功能**：清洗、烘干、喷嘴清洁、固件升级、恢复出厂都没有实现。

这个集成不是安全系统，不要用它来做就座检测或机械保护。

## 局限

- 只实现了 ZS800J 这一套协议，也只在一台机器上实测过。
- 协议里没有请求编号，一条很晚才到的回报，可能被当成这次查询的新结果。
- 实验性控制的编码来自对官方小程序行为的分析，还没在真机上验证。

## 开发

复现隔离的 HA 生命周期检查时，使用官方 2026.9.1 镜像，带上
`--network none --memory 2g --cpus 2 --rm`，将当前仓库只读挂载到 `/repo`，
执行 `python3 /repo/tests/ha_smoke/smoke_in_ha_container.py /repo`。
再在 `/repo` 后分别加 `--uncertainty` 和 `--handoff` 各运行一次，验证卸载失败
时的保守处理，以及连接接管前掉线经真实 HA 适配器、协调器和实体传播后的释放与手动恢复。
不要挂载生产配置或蓝牙硬件。

```sh
python -m unittest discover -s tests -v   # 协议 + 模拟蓝牙 / 实时流
python scripts/sync_library.py --check    # 检查 lib/ 与 jomoo_ble/ 是否一致
python scripts/check_repository.py        # 编译、链接、确认没有真实 MAC 或内网 IP
ruff check . && ruff format --check .
```

`tests/ha_smoke/smoke_in_ha_container.py` 会在真实的 Home Assistant Python 环境里，拿一台模拟马桶跑完整个集成。覆盖配置流程、实体、服务、迁移、HA 原生蓝图、选项、诊断和卸载。不要对着生产环境的配置目录跑它。

协议细节见 [docs/protocol.md](docs/protocol.md)，验证记录见 [docs/verification.md](docs/verification.md)。
