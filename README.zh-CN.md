# ha-jomoo-ble

[English](README.md) · Apache-2.0 · 非官方 Home Assistant 自定义集成

在 Home Assistant 里通过本地蓝牙控制 **九牧 ZS800J** 智能马桶。蓝牙可以走 HA 本机任意可连接的蓝牙适配器，也可以走放在马桶旁边的 ESPHome 蓝牙代理。不连云端，不用账号，不含任何厂商代码。

<!-- STORY:START -->
## 为什么做这个

我们家的马桶离淋浴太近了。

九牧 ZS800J 有个很贴心的功能叫「自动翻盖」：人一靠近，盖子自己掀开。可一到洗澡的时候，它就变得不太聪明——人站在旁边冲水、水汽飘过去，盖子就被一次次掀起来，敞着口对着淋浴区。

所以这个项目最初、也是最终的目标只有一句话：

> **热水器正在出热水的时候，把马桶的自动翻盖关掉；停水之后，再恢复成原来的样子。**

「恢复成原来的样子」很重要：如果洗澡前自动翻盖本来就是关的，洗完也不会被擅自打开。

为了做到这件事，我们需要先让 Home Assistant 真正“听懂”这台马桶——于是有了这个集成。

## 开发过程（简版）

1. **先解决“够不着”。** 马桶只有蓝牙。我们把一块 M5Stack CoreS3 刷成 ESPHome，当作蓝牙代理放到马桶旁边：放得远时信号约 -90 dBm，连一次要十几秒；挪到旁边后约 -68 dBm，不到 1 秒就能连上。
2. **用官方微信小程序做“对照组”。** 九牧官方的控制入口是微信小程序。我们以它为对照基准：弄清这台型号对应的协议版本、每个状态字段的含义，再用自己的蓝牙连接做**只读查询和数据回读**，逐个字段和小程序、和马桶上的实际状态核对。这一步把“猜协议”变成了“对照验证”。本仓库**不包含、也不需要**任何厂商代码或小程序文件，实现完全独立编写。
3. **分步实机验收。** 顺序是：只读 → 可恢复的动作 → 设置项。开盖、关盖、开座圈、关座圈、小冲、自动翻盖关/开，全部逐项上机验证。每条控制指令都会带上完整设置，所以每次都先读当前设置、原样带回，再对比前后，确认水温、座温、风温等没有被“顺手”改掉。
4. **一个意外的旁证。** 验收关盖时，盖子关好几秒后又自己打开了——原来是人正站在马桶前看，自动翻盖感应到了。这恰好就是这个项目要解决的问题。
5. **接入 Home Assistant。** 马桶每次被连接都会“嘀”一声，而且同一时间只允许一个手机/网关连接，所以集成默认**不做周期轮询**，只在你点刷新、执行动作或联动触发时短暂连接，用完立刻断开。
6. **淋浴联动。** 集成提供「暂停 / 恢复自动翻盖」两个服务，会记住暂停前的状态；配合蓝图，把任意“热水器正在出热水”的传感器接进来即可。
<!-- DEVLOG:END -->

## 能做什么

- **按需读取状态**：
  - 上盖和座圈的位置，是否在运动；
  - 是否有人就座、是否在冲水、当前工作状态；
  - 缺水、水流异常、传感器或过温故障；
  - 滤芯剩余百分比和已用小时、泡沫液不足；
  - 各项设置档位，以及上次刷新时间。
- **已验证的控制**：开盖、关盖、开座圈、关座圈、小冲，以及「自动翻盖」开关。
- **淋浴守护**：提供 `jomoo_ble.suspend_auto_cover` 和 `jomoo_ble.resume_auto_cover` 两个服务，外加一份自动化蓝图。热水器出热水时关掉自动翻盖，停水后恢复成原来的样子。
- **实验性控制**（默认关闭）：
  - 档位类：水温、座温、暖风温度、臀洗水压、臀洗喷嘴位置、暖风风速、宽幅洗；
  - 开关类：自动冲水、自动夜灯、UV 水路杀菌、关盖冲水、自动小冲、脚感、氛围灯；
  - 动作类：大冲。

## 硬件

- **马桶**：九牧 ZS800J，蓝牙广播名是 `JOMOO_SMART_237369`。其他型号会被拒绝。
- **蓝牙连接**：HA 到马桶之间要有一条能主动连接的蓝牙链路，可以是本机蓝牙适配器，也可以是开了 `active: true` 的 [ESPHome 蓝牙代理](https://esphome.io/components/bluetooth_proxy/)。
  - 卫生间对蓝牙信号衰减很大，代理要放在马桶附近。实测隔墙约 -90 dBm 时基本连不上，放到旁边约 -68 dBm，不到 1 秒就能连上。
  - 注意防水和用电安全。
  - 用 ESPHome 代理时，还要在 HA 里打开这台 ESPHome 设备的集成选项，把「蓝牙扫描模式」设为「主动」。新版 HA 默认是「自动」，大部分时间只被动扫描，马桶的名字（只放在扫描响应里）到不了 HA。这时集成会把它当成不支持的型号拒绝连接，重载后所有实体都会变成不可用。ESPHome 配置里写 `active: true` 管不到 HA 这一侧的设置。

## 先知道两件事

1. **每次连接，马桶都会「嘀」一声。** 所以集成默认不轮询，只在下面三种情况下短暂连接，用完立刻断开：
   - 点「刷新状态」；
   - 调用 `jomoo_ble.refresh`；
   - 执行控制。
   如果需要定时刷新，可以在选项里开启，间隔 300 秒到 24 小时。
2. **同一时间只能有一个设备连马桶。** HA 连着的那几秒里，官方小程序连不上，反过来也一样。添加集成前请先关掉小程序。

## 安装

**通过 HACS 安装（自定义仓库）**：
1. 打开 HACS → 集成 → 右上角 ⋮ → 自定义存储库；
2. 填入 `https://github.com/xiaoyaner0201/ha-jomoo-ble`，类别选「集成」；
3. 安装后重启 HA。

**手动安装**：把 `custom_components/jomoo_ble` 整个目录（含 `lib/`）复制到 HA 的 `config/custom_components/` 下，然后重启 HA。

**添加设备**：
- 进入「设置 → 设备与服务」，马桶通常会被自动发现。
- 如果没有被发现，点「添加集成 → JOMOO BLE」，填入马桶的蓝牙 MAC 地址。只要附近能看到匹配的广播，这一栏会自动填好。文档里的 `02:00:00:00:00:01` 是虚构的示例地址。
- 添加时会做一次只读查询，马桶会嘀一声。

## 选项

| 选项 | 默认 | 含义 |
| --- | --- | --- |
| 启用已验证的控制 | 关 | 翻盖、翻圈、小冲、自动翻盖、淋浴守护 |
| 启用实验性控制 | 关 | 下表中标为「实验」的全部功能 |
| 自动刷新间隔 | 0（关） | 填 0，或 300 到 86400 秒 |
| 持续实时状态 `enable_status_stream` | 关 | 持有一个共享 BLE 连接；启用时忽略轮询间隔 |

### 可选实时采集（候选，未完成实机验收）

在集成选项中明确开启「启用持续实时状态」。首次连接会响，且 HA 将持续占用唯一
central，官方小程序不能同时连接。关闭选项、卸载集成或停止 HA 才释放蓝牙；
若断开无法确认，阻断控制并显示诊断，不声称手机已经可以连接。

启动只尝试一次连接，初始查询完整且校验过的 E2/EA/E9/FA/E7 后，以被动通知
更新已有实体（含「冲水中」）。流、手动刷新、控制、淋浴守护共享原 SessionManager
的同一物理连接和操作锁。控制仍每次全新查询，保留设置、只写一次并读回；
不拿流缓存拼控制帧。没有周期性查询/断开重连，也没有自动重连循环。
断线后相关状态 unavailable，点击已有「刷新状态」或明确调用 `jomoo_ble.refresh`
才允许一次合并恢复尝试；底层原有有界 establish 重试不叠加。

仅开启时新增「实时状态连接」「上次收到状态」两项诊断。接收时间只随合法包变化，
属性给出各帧时间；静默不冒充新状态，断线前缓存不继续当 live。
「上次刷新」仍表示主动完整查询完成时间。连接状态不是心跳，静默不能证明所有
字段仍然新鲜。FA payload[5] bit0 仍未知，没有命名为补水/水位/补满，没有新增
补水传感器，更没有泵策略或跨设备服务。联动由 HA 原生 automation 另行配置。

本候选只通过合成 BLE 与真实 HA 容器生命周期验证，未连接真实马桶或生产 HA。
真实代理长连接、蜂鸣、单 central 释放、掉线及日常稳定性需父侧实机验收。
完整语义与边界见[实时采集说明](docs/status-stream.md)。

## 实体

| 实体 | 类型 | 状态 |
| --- | --- | --- |
| 刷新状态 | 按钮 | 已验证（只读） |
| 开盖 / 关盖 / 开座圈 / 关座圈 | 按钮 | 已验证 |
| 小冲 | 按钮 | 已验证 |
| 大冲 | 按钮 | 实验，默认禁用 |
| 自动翻盖 | 开关 | 已验证，带属性 `guard_active`、`guard_pending`、`guard_previous` |
| 自动冲水、自动夜灯 | 开关 | 实验，默认禁用 |
| UV 水路杀菌、关盖冲水、自动小冲、脚感、氛围灯 | 开关 | 实验，默认禁用 |
| 水温 / 座温 / 暖风温度档位、臀洗水压、臀洗喷嘴位置、暖风风速、宽幅洗 | 数值 | 实验，默认禁用（这些是设备档位，不是摄氏度） |
| 上盖、座圈、上盖运动中、座圈运动中、有人就座、冲水中 | 二元传感器 | 只读 |
| 缺水、水流异常、传感器或过温故障、滤芯需更换、泡沫液不足 | 二元传感器 | 只读 |
| 淋浴守护生效中 | 二元传感器 | 只读 |
| 工作状态、滤芯剩余（%）、滤芯已用（h）、妇洗水压 / 喷嘴位置、上次刷新 | 传感器 | 只读 |
| 原始 E2 / FA / E9 / EA / E7 | 传感器 | 诊断用，默认禁用 |

**「已验证」和「实验」的区别**：
- 已验证：指令在真实的 ZS800J 上实际发过，读回设备状态确认生效，而且其他设置一个都没变。
- 实验：沿用同一套帧结构，但还没在真机上跑过。它同样会读回确认，设备没有确认就不会报成功。

**这台马桶的两个特性**：
- 盖子和座圈是联动的：开座圈会连带开盖，关座圈时盖子保持开着。
- 自动翻盖会感应站在马桶前的人，所以刚关好的盖子，如果有人站在前面，可能会自己再打开。

## 淋浴守护

先导入蓝图：

[![在你的 Home Assistant 中打开蓝图导入对话框](https://my.home-assistant.io/badges/blueprint_import.svg)](https://my.home-assistant.io/redirect/blueprint_import/?blueprint_url=https%3A%2F%2Fgithub.com%2Fxiaoyaner0201%2Fha-jomoo-ble%2Fblob%2Fmain%2Fblueprints%2Fautomation%2Fjomoo_ble%2Fshower_guard.yaml)

蓝图需要三项输入：
- 一个「正在出热水」的二元传感器；
- 马桶的「自动翻盖」开关；
- 恢复延迟，默认 3 分钟。

运行逻辑：
- 一出热水，就暂停自动翻盖；
- 停水并持续到设定的延迟，就恢复；
- 每一步最多重试 5 次，每次间隔 30 秒，直到 `guard_active` 属性变成目标值。

**选信号要注意**：用来触发的必须是「正在用热水」，而不是「热水器通电」。接好以后先洗一次澡，看这个信号的历史记录确实变过、自动化的「上次触发」有时间，再放心用。

**实测搭配（已更正）**：作者家是国行史密斯燃气热水器，通过社区集成 [Ai-Link A.O. Smith](https://github.com/mopocv/Ai-Link_A.O.Smith) 接入 HA。要用 v1.4.0 及以上，它会自己续期 App 的短效令牌。

本文旧版推荐用它的「燃烧加热状态」，这是错的：这台机器上它连着好几天一直是「未加热」，真洗澡时风机约 3000 转、燃烧比例 44%，它也没变，守护一次都没触发。流量读数也不可靠，出现过没开水龙头、流量却不为零的情况。

作者家现在用的触发条件是：**零冷水开着，或者风机转速大于 0**。零冷水循环和其他用热水的时候也会触发，后果只是自动翻盖暂停一会儿。实体名换成你自己的；两个来源都不可用时，模板保持原值，不会把「没数据」当成「停水」：

```yaml
template:
  - binary_sensor:
      - name: 正在用热水
        unique_id: hot_water_in_use
        state: >-
          {% set recirculation = states('switch.water_heater_recirculation') %}
          {% set fan = states('sensor.water_heater_fan_speed') %}
          {% if recirculation in ['unknown', 'unavailable'] and not is_number(fan) %}
            {{ this.state == 'on' }}
          {% else %}
            {{ recirculation == 'on' or (fan | float(0)) > 0 }}
          {% endif %}
```

蓝图里的恢复延迟建议设成 **10 分钟**，免得擦身、穿衣时又开始翻盖（蓝图默认仍是 3 分钟）。热水器云端数据有时也会连着几分钟不更新。

**HA 重启或改自动化之后的兜底恢复**：HA 重启、或者自动化被保存/重载时，正在计的「停水满 N 分钟」会作废。守护状态还在，但不会再有人去触发恢复。下面这个兜底自动化每 5 分钟、以及 HA 启动时检查一次，停水满同样的时长就恢复；不需要恢复时不会连马桶。实体名换成你自己的，延迟和蓝图保持一致：

```yaml
automation:
  - alias: 淋浴守护兜底恢复
    mode: single
    triggers:
      - trigger: time_pattern
        minutes: "/5"
      - trigger: homeassistant
        event: start
    conditions:
      - condition: template
        value_template: >-
          {{ is_state('binary_sensor.hot_water_in_use', 'off')
             and (state_attr('switch.toilet_auto_cover', 'guard_active')
                  or state_attr('switch.toilet_auto_cover', 'guard_pending'))
             and now() - states.binary_sensor.hot_water_in_use.last_changed
                 > timedelta(minutes=10) }}
    actions:
      - action: jomoo_ble.resume_auto_cover
        target:
          entity_id: switch.toilet_auto_cover
```

HA 重启后，信号的 `last_changed` 也会从头算，所以兜底最多会再多等 10 分钟。作者家的 HA 里跑的是同样的逻辑；用之前请在你自己的 HA 里验证。

**守护规则**：
- 暂停时，先记住当前自动翻盖的状态，只有原来是开着的才会去关。
- 恢复时，只有原来是开着的才会打开，绝不会主动写「关」。
- 守护生效期间，如果你手动拨了自动翻盖开关，守护会被取消，以你的手动设置为准。
- 守护状态会保存下来，HA 重启后不会丢。

## 安全设计

- **写之前先确认能写**：每次写入前，都会在同一次连接里读一遍 E2、FA、E9、EA 四组状态，马桶不在待机就拒绝。开关盖、翻圈、冲水这类动作，在有人就座、盖子或座圈正在动的时候也会拒绝。
- **只改要改的那一项**：每条控制指令都带着全套设置。集成用刚读到的最新设置重新组装指令，所以其他设置不会被顺手改掉。
- **写完一定读回核对**：
  - 写完后会反复读，直到确认目标生效；
  - 然后逐项核对其他已知设置，只要有一项变了就报错，并给出前后差异。
- **冲水的确认方式**：冲水指令发出后，如果约 6 秒内没看到「冲水中」的标志，会记一条警告，结果标为「已发送、未确认」。
- **绝不自动重试**：写入失败时指令也可能已经到了马桶，所以不会自动重发，也不会先把状态显示成「成功」。
- **断开状态不明就停用**：如果没法确认连接已经断开，集成会停止再发起连接，直到重新加载。
- **不做的功能**：清洗、烘干、喷嘴清洁、固件升级、恢复出厂都没有实现。

这个集成不是安全系统，不要用它来做就座检测或机械保护。

## 局限

- 只实现了 ZS800J 这一套协议，也只在一台机器上实测过。
- 协议里没有请求编号，一条很晚才到的回报，可能被当成这次查询的新结果。
- 实验性控制的编码来自对官方小程序行为的分析，还没在真机上验证。

## 开发

```sh
python -m unittest discover -s tests -v   # 协议 + 模拟蓝牙 + 淋浴守护
python scripts/sync_library.py --check    # 检查 lib/ 与 jomoo_ble/ 是否一致
python scripts/check_repository.py        # 编译、链接、确认没有真实 MAC 或内网 IP
ruff check . && ruff format --check .
```

`tests/ha_smoke/smoke_in_ha_container.py` 会在真实的 Home Assistant Python 环境里，拿一台模拟马桶跑完整个集成。覆盖配置流程、实体、服务、淋浴守护、选项、诊断和卸载。不要对着生产环境的配置目录跑它。
